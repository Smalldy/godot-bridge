# 任务中心 —— 方案（P-1）

> 本文档是「方案」这一文档类型的第一个实例：`status: settled` 指**方向已冻结**，不是细节已定。
> 下面第七节列出的待定项属于实现选择，不构成方向变更。

## 当前设计（一页版）

> **本节是权威表述。** 第二节之后的细述是按时间累积的，其中若干处记录的是**当时被推翻的做法**；与之冲突时**以本节为准**。

**参与者与边**。用户 · 对话Agent（与用户对话）· 任务系统（用户与它「交互」）· WorkAgent（住在任务系统里）。边：用户↔对话Agent（会话，✅）· 用户↔任务系统（面板路由，✅）· 对话Agent→任务系统（`task_center` 工具，✅）· 任务系统→对话Agent（推送/唤醒，机制已确认、未实现）· **任务系统→WorkAgent（框架触发，❌ 唯一缺失的边）**。

**两个客户端，一个 API**。任务系统对外是一个 API；**用户（面板）与对话Agent（工具）是它的两个客户端**——所以两者必须共用一份状态与一套规则（实现上即 `state.mjs` + `service.mjs`）。

**任务的归属与生命周期**。

- **`draft` 是对话自己的工作清单**：由对话Agent 或用户完成，**不进池子**。它的生命周期就是 **draft → done**，不经过 queued/claimed/in_progress。
- **发布（入队）** 才进池，需用户同意。`queued` = 在池里等人做。
- **派发是系统内部机制**：把池里的任务交给某个 WorkAgent（选人、启动、交接）。客户端看不见也不调——`claim` / `release` / `reserve` 因此**不是 API 方法**，`in_progress`/`claimed` 只是派发在板上的**可见投影**。
- **没有「领取」**：退队即**「退回草稿」**（queued → draft）。已派发的任务用「取消」。
- 池内的活完成 → `review` → **由用户关闭**；对话自己的活 → **由对话Agent 标记完成**。

**对外 API = 关于工作的决定**：`overview` / `list` / `show` · `create` / `update` / `cancel` / `reopen` / `block` / `unblock` · `close` · `publish` / `unqueue` / `reorder` · `locks` / `requestLock` / `releaseLock` / `forceRelease` · `getSettings` / `setSettings`。
**需同意**是一条**统一规则**（对话Agent 调用 `publish`/`unqueue`/`reorder`/`forceRelease` 时返回 `needs-consent` + 计划，用户确认后生效；用户自己调用永不需同意），不是一张例外表。

**内部职责 = 谁在什么时候做哪件事**：派发与触发 · 依赖就绪调度 · 租约与接管重试 · 并发预算与运行锁 · 锁仲裁与回收 · 唤醒 · 推送与去重 · 持久化与一致性 · 依赖校验 · 审计。

**依赖**：发布是**依赖闭包**（只拉仍是草稿的前置；前置被取消或 id 悬挂则拒绝）。调度器只派发**前置全部 `done`** 的任务。**已派发 ≠ 已完成**，所以前置可能永远完不成 → 下游标「**依赖已破**」交用户决定（取消 / 改依赖 / 显式覆写强行放行，覆写记进审计）。派发门槛只解决"不能提前开工"，不解决"永远开不了工"。

**文件协作**：只用**文件锁**（worktree 已评估并暂缓）。键 = 项目相对路径，持有者 = agent；预约按请求时间排队，**释放时在同一提交内授予等待最久者**；租约兜底、存活判断优先；**只存宿主内存**。

**摘要与通知**：`/task` 给一次板子摘要（已实测）；事件驱动推送 + 内容哈希去重 = T-7。**唤醒与派发已实现并实测**（`spawnTeammate` / `sendMessage`；空闲目标 `coldResume`；`agent/status` 事件确实到达 profile 行）——那条"任务系统→WorkAgent"的边**不再是缺失的**。仍缺的是**租约回收**：worker 做了一半沉默或死掉后，没有任何东西把任务收回池子（实测：两条任务的租约已过期，仍停在 claimed/in_progress）。

## 一、结论

**任务中心 = 项目级、跨会话的共享工作上下文**，由三部分组成：文档、任务、工作台。三者寿命不同，必须分开：

| 概念 | 容器 | 寿命 |
|---|---|---|
| 讨论 | DSH 原生会话 | 会话级；可 fork/恢复 |
| **方案** | 项目内文档 | 跨会话；会被取代 |
| 任务 | 项目内任务板 | 跨会话 |
| 任务计划 | 项目内文档 | 跟随任务 |
| 文件锁 | 宿主内存 | 分钟～小时 |

**先做任务管理**（工作台最后），因为另外两个模块都产出或消费任务。

宿主里已有的近邻原语不能重复造：计划模式是**会话内一次执行**的提案-批准；`goal` 是**每会话至多一个**且不调度工作。**"项目级、被讨论过、被冻结的方向"在 DSH 里没有原语承载**——这正是本方案要补的缺口。

## 二、任务从哪里来

```
原生会话讨论（零侵入，插件不参与）
        │  用户敲 /task
        ▼
   agent 拆解为「任务草稿」
        │  用户在面板里「发布到队列」
        ▼
        队列 → agent 领取
```

**整条链上没有任何一步可以由 agent 自己启动。** 两个授权点：

1. **敲 `/task`** —— 允许创建真实任务。
2. **面板里点发布** —— 允许进入队列。

agent 可以先报告打算建什么再等你确认，也可以先建后报：**草稿本身无害**，真正的安全阀是发布那一步。

## 三、`/task` 命令（已实现并实测）

- **必须注册**：未注册的斜杠行会被适配器**直接拒绝**，不会变成提示词。
- **命令自己进不了模型**：`dsh-commands` 在宿主上执行命令、不产生模型消息；命令的返回文本只渲染在 UI 里。
- **信号靠 `Agent` 送进去**，照抄 `dsh-plan-mode` 的 `/plan <message>`：

  ```js
  agent.steer(createUserMessage({ content, source: { kind: 'user' } }))
  ```

  `createUserMessage` 来自 `@deepseek-ai/dsh-llm`，**动态 import**：解析不了只会让 `/task` 回一句可读错误，不会拖垮整个插件模块。
- 命令后的自由文本原样追加为 `rawInput`，所以**不需要子命令**；顺序交给 agent 判断。
- `recordInput` 保留默认值 `true`，于是 `/task` 本身留在会话日志里——将来"这个方案是哪个会话产出的"有据可查。

实测记录：连发三次 `/task`（含附加文本与空 `rawInput`），信号每次都作为**一条用户消息**到达模型，命令自身的结算文本均未进入模型。

## 四、任务板与数据落地

**一个文件**：`<被工作的项目>/.agents/tasks.json`

不为它建目录——今天只有一份数据；真出现第二个文件时再升成目录（一次 `git mv` ＋ 改一个路径常量）。

- **并发**：`fs.stat` 取 `FsInfo.version`，写用 `fs.writeText(target, content, { kind: 'replaceIfVersion', version })`，冲突报 `FS_STALE_VERSION`。契约保证 mutation 是原子的。
- **写入纪律**：进程内先串行化；收 `FS_STALE_VERSION` 时**重读并重放变更函数**（不是重放旧内容），重试 ≤3 次。这样用户手改板子或多个宿主同时写都不会互相覆盖。
- **变更通知**：`fs.watch(board)` → 失效内存缓存 + 推给面板。它可能在 provider 不支持时 throw，必须降级成轮询。
- 选文件而非 `storageDomain` 的理由：`storageDomain` 是 **profile 级**（不是项目级）、`domain/changed` **只在本进程可见**、且**没有数据迁移**（改 schema 直接拒绝开域）。文件还带来可移植、插件卸载后仍可读。
- **板子不进 git**（写进项目的 `.gitignore`）。它是**运行态**，不是源码：提交它会让它在分支间来回漂移，并在合并时制造我们正想避免的冲突。**进 git 的是方案文档**——那才是需要被 review、被版本化的产物。这条同时消掉了"板子只认主工作树"的复杂度：没有 worktree，就没有第二份检出。

### 文件锁（取代 write_scopes）

`write_scopes` 已删除：**任务在执行前无法声明它会碰哪些文件**，那个声明永远无法被校验、也永远不真。文件锁是可确定、可观察、可排队的。

- 键 = 项目相对**文件路径**；持有者 = **agent（会话）**，不是任务；锁上可带 `taskId` 只作展示标签。
- **持有者标签由 session id 合成**（`@` + 去前缀后的前 8 位）。依据是 live `tools` 服务契约：`interface Agent { readonly id: SessionId }`——**agent 上没有名字**，面板 mock 里 `@fixer` 那种是 Agent Teams 名字，这一层看不到。已知限制，将来若有服务暴露名字可替换。
- 每个锁带**租约**（见下）。
- **预约**按请求时间排队；**释放时在同一提交内授予等待最久者**，文件永不出现"无人持有却有等待者"的中间态。
- 对同一 agent **幂等**：已在队列中再申请，**保留原始请求时间**（否则反复询问会把自己的优先级洗掉）。
- **读取不需要锁**，但任何 agent 都能查到"谁正在写"。
- 锁**只存宿主内存**，不落文件：写频率高（agent 每动一个文件一次写），和任务记录挤同一文件会互相打断 CAS；宿主重启后持有者已不存在，锁本就该失效。代价是第二个宿主进程看不到它——与已声明的单进程假设一致。

下面四条是检索外部先例后补进设计的（见「协作策略」一节的出处）：

- **租约过期时通知持有者**（"你对 X 的锁已过期"）。不通知的话，agent 会以为自己仍独占而继续写——先例里明确做了这件事。
- **agent 退出时 releaseAll**，不要指望它逐个释放。
- **键支持目录/glob 前缀**（锁 `scripts/core/*` 挡住里面的文件）。原先把目录粒度推迟了，先例把它当基本功能。
- **回收以 PID 存活为准，时间租约只作兜底**（宿主进程内可判；跨进程时退回 TTL）。

#### 租约的职责边界

租约回答的是"**持有者还活着、还在干活吗**"，作用是把**永久死锁换成最多阻塞 N 分钟**。非有不可，因为 agent 的死法很多：宿主崩溃、用户中止本轮、模型报错、会话被关，以及**它就是忘了释放**。最后一条最要紧，也是锁和数据库事务的根本区别——**释放不是事务边界，而是一次模型决策（一次工具调用）**，而模型忘掉一次工具调用是常态。没有租约，这五件事里任何一件都让文件永久被锁、其他 agent 永久等待：**一次崩溃就能让项目不可编辑。**

**租约与存活判断覆盖的是不同的故障，不是两层同一件事：**

| 故障 | 存活判断 | 租约 |
|---|---|---|
| 持有者进程死了 | ✅ 立即回收 | 不必等它过期 |
| 持有者**活着但卡住**（Godot 启动挂起、子 agent 不返回、模型反复重试） | ❌ 看起来一切正常 | ✅ 唯一能发现它 |
| 持有者**活着但忘了释放**（编辑完注意力走了） | ❌ | ✅ 常态故障 |

**过期必须通知持有者。** 静默过期会开一个新洞：持有者以为仍独占而继续写，锁却已经给了别人 → **两个写者**。通知是这个机制的配套，不是可选优化。

**连锁效果：** 有了存活回收，租约只需管"活着但不干活"，所以 TTL 可以放宽而不伤别人；而**续约本身就是心跳**——"还在续约"= "还在动这个文件"，锁因此从**互斥量**升级为**活动指示器**，而"谁正在写"正是其他 agent 最想知道的信号。

**它安全的前提是任务 9（工具边界强制）。** 租约过期之所以能安全释放，是因为下一个写会**响亮地失败**而不是静默双写；**没有任务 9，租约就是危险的**，两件事必须一起上。

**取值**：TTL **10 分钟**（先例是 5 分钟；我们已有存活回收兜底，所以可以放宽），**续约在每次写尝试时发生**（顺带即心跳）。锁只存宿主内存，宿主重启全清，所以**租约不是持久化问题**。

**任务租约与文件锁租约后果不同。** 文件锁过期会放别人进来写；任务认领过期只是让任务看起来"卡住"。所以任务租约**不自动改派**——否则会把任务从仍在工作的 agent 手里抢走——只把它标成「⚠ 租约已过期，可能无人推进」，由用户或别的 agent 决定。

### 协作策略：只用文件锁（worktree 已评估并暂缓）

原先设想两种策略（文件锁 / git worktree）加一个「自动」（git 项目走 worktree，否则走锁）。**现决定只做文件锁**，worktree 暂缓；设置项也**先不做**——只有一个可选项时不值得建设置。检索到的依据（2026-10）：

- [Claude Code 官方文档](https://code.claude.com/docs/en/worktrees)把 worktree 做成一等功能（"Isolate sessions with worktrees"），但需要**四道强制检查**——编辑目标落在主检出、命令 cwd 解析到主检出、把 git 重定向进主检出、以及无法从命令文本确认的命令，全部拦截。它同时**写明漏洞**：这些检查不追踪 shell 命令实际写了哪些文件，`cp` 或重定向写进主检出**不会被拦**。
- [flightdeck 的协调层文档](https://github.com/justinchuby/flightdeck/blob/HEAD/packages/docs/guide/coordination.md)有完整的 `WorktreeManager` 实现却**至今未启用**，理由写在文档里："依赖 agent 环境有正确的 git 设置，这在所有部署上下文里不保证"（例如每个 worktree 要单独 `npm install`），并且**创建失败时回退到共享工作目录**；它实际在跑的是文件锁。
- [一份事故驱动的 worktree 纪律文档](https://github.com/VMAFx/vmafx/blob/27f5a25fe42c88b5d1ba49e6634b6d230e7fc2f4/docs/development/agent-worktree-discipline.md)记录 worktree 的首要失败模式是 **drift**（agent 的 cwd 落到主检出，于是提交进用户的分支、冲掉未提交改动），**一个会话里五次事故**，最后靠宿主侧 pre-commit 闸门兜底。它的结论值得记住：只靠 agent 自律脆弱，只靠宿主闸门有窗口——两层都要。

对我们是**放大器的两端**：worktree 顺利时并行度更高，出事时代价更大。Godot 特有的两件事让它更贵：

- **`user://` 按项目名定位，不是路径。** 本机 `app_userdata` 下的目录名全是项目名，所以同项目的两个 worktree **共享存档与日志**——而本插件 `godot_run_project` 启动的游戏日志正写在 `user://logs/`。worktree 模式下跑游戏必须额外按项目名串行（一个新的锁种类），或给每棵树改 `application/config/name`。
- **`.uid` 是入库文件**（本仓库自己就提交了 `plugin/godot_operations.gd.uid`）。检索到两篇专讲 Godot UID 在合并后错乱/重命名后冲突的文章，但**只拿到标题、未读到正文**，所以不作为证据；要下结论需自己实测（两棵 worktree 各建同名脚本，看 UID 是否相撞）。

**若将来重启 worktree**，需要先具备这四条，它们都不便宜：主检出保护（拒绝写入）、板子从主工作树读取穿透（Claude Code 对 `.claude/skills`/settings 就是这么做的）、跑游戏按项目名串行、以及每棵树各自的 Godot 导入环境。所以"先只用锁"不是妥协，是排序。

### 认领为什么不自动

面板上的「领取」是这个模型里最容易被误读的按钮（用户第一眼就问"不是自动认领吗"），所以把判断写下来。

**宿主无法让空闲的 agent 开始干活。** agent 只在会话收到消息时运行，它不轮询队列。因此"发布时自动指派"只会产生**一条写着进行中却没人做的任务**——比排队更糟，因为它看起来有人在做，是在撒谎。

于是「领取」服务的是**人**，不是 agent：它是"这条我自己做，别让 agent 抢"（记录为 `@user`），顺带在开工前公开"谁在做"，并建立**租约**——面板的倒计时与「⚠ 租约已过期」都建在租约上。agent 那边的对应动作是 `task_center claim`；而按钮文案写成「领取」在混合板子上确实不够清楚，应改为「自己领取」。

**让它"感觉自动"的正确做法是通知，不是指派。** 形态应该是：用户发布 → 插件告诉相关会话「队列变了，这是队列头」→ agent 去领。这正是 **T-7**（事件驱动摘要 + 内容哈希去重）的职责；它依赖 `agent.followup()` 唤醒空闲 agent，而该机制**尚未验证**（见第八节）。若验证通过，认领不再需要人按，「领取」退化为"我自己来"一个用途；若不通过，认领保持显式。

**所以顺序上应先验证 `agent.followup()`——它决定队列能否自己动起来**，比继续加功能更优先。

### 队列只装交给 agent 池的任务

**队列是 agent 的工作清单。** 一条用户打算自己做的任务没有任何理由先进池子——而按现在的模型它必须绕一圈（发布进池 → 领取出来），且**中途暴露在抢单风险里**：`queued` 的任务任何 agent 都能领走。

缺的概念是：**发布要带对象**。

| 发布对象 | 结果状态 | 进队列吗 |
|---|---|---|
| agent 池 | `queued` | 是——队列唯一该装的东西 |
| 某个人（`@user`） | 直接 `in_progress`，`assignee` 为该人 | **否，从头到尾不进池子** |

顺着这个洞牵出的另外两处：

- **面板的「新建」也不该默认造草稿。** 草稿的语义是"agent 提出、等用户授权"，而**用户自己建的任务本来就是授权过的**。
- **不带租约的指派必须不可被抢。** 今天的 `claimTask` 只拦"有活跃租约"的持有者，而人的指派没有租约（人不会超时），于是 `leaseUntil === null` 被判成"没被持有"——**agent 能把人的任务领走**。正确规则：**带租约的 `assignee` = agent 的认领（会过期、过期可接管）；不带租约的 `assignee` = 明确指派（永不过期、永不被抢）**。这也让人不需要"续约"这种荒唐动作。

按钮故事由此自洽：草稿上给 **发布**（交给池子）与 **我来做**（直接归你）；池子里的任务给 **自己领取**（从池里拿走）。**队列里永远只有交给池子的任务。**

### 模型修订：草稿是对话的工作清单，池子有等待队列

用户给出的五条，逐条评估后成立，其中第 1–2 条**修正了本方案原先的倒置**。

1. **草稿是你我商议的产物，不在池子里是对的。**
2. **草稿中的任务由对话里的 agent（我）或用户自己完成。** 原先把草稿当作"未被授权的工作"是**倒置**的——工具因此拒绝认领草稿（`not-released`）。正确语义：草稿是**这场对话自己的工作清单**，只有用户决定交给别人时才进池子。配套规则：**对话内领取不带租约**（对话成员不会超时），**池内领取带租约**——租约正是区分两者的东西。
3. **发布可以由 agent 发起，但等用户同意。** 这**推翻**了原先"工具硬拒绝 publish"的决定。agent 做跑腿（算依赖闭包、组装计划、说清后果），**授权仍在用户手里**，机制复用两阶段确认。请求要**记在任务上**（`releaseRequested`）而不是只发在聊天里，否则会话一关就消失。
4. **池内领取前检查前置是否完成；未完成则不能领取，转而加入该任务的等待队列。** 这条让"拒绝领取"从坏体验变成好机制：原先主张"报告而不拒绝"的理由是**被拒绝的 agent 无事可做**，而等待队列取消了这个理由。**主张收回，拒绝对。**
5. **前置完成后唤醒队列中的第一个等待者。** 与文件锁同一条"等待最久者优先"规则。

第 4–5 条有两个必须先解决的问题：

- **唤醒依赖 `agent.followup()`，而该机制未验证。** 没有它，等待队列只是一张没人看的名单。它因此是**前置中的前置**：等待队列、发布通知、事件驱动摘要（T-7）三件事都卡在它身上。
- **死掉的等待者会卡住队首。** 唤醒第一个等待者时若它已不在，必须顺延——所以**"唤醒"自身需要一个租约/超时**（与文件锁同族），否则一个消失的 agent 永久占住队首。

**协议层的硬问题：宿主分不清"对话里的 agent"与"池内 agent"。** 两者都只是会话在调工具（`Agent` 只有 `id`，见第八节）。所以"池内 agent 不得领取草稿"无法直接强制。两条路：在任务上记**来源会话**并按它放行（会话恢复/换会话时不可靠），或**只做可见性**——草稿不进队列列表（已经如此），池内 agent 看不到它，知道 id 硬领也无实害且面板可见。**倾向前者暂不做、先只做可见性与记录创建者**；同时要查"是否存在区分 teammate 与 lead 的服务"，若有，那里才是该判定的正确位置，而不是本插件自行发明。

**第 6 条（用户补充）：对话里的 agent 不是池内 agent。** 池内 agent 由**框架管理、框架触发**；对话里的 agent 是**用户的协作伙伴**，不在那个范围内。因此：

- **对话里的 agent 不从池子里认领。**"领取"是池内 agent 的动作。
- 它要做队列里的活，走**申请**：申请把任务移出队列 → 用户同意 → 自己做 → 标记为完成。
- **这条顺带解决了上面那个"宿主分不清两种 agent"的难题**：区分落在**动词**上，不落在身份上——对话里的 agent 用「申请 / 报告」，池内 agent 用「认领」。于是不需要任何身份判定，也不需要"来源会话"这类近似。
- 它自己的工作**不设验收闸门**（用户就在旁边看着），但 `done → in_progress` 的 reopen 保持合法——用户的复核权没丢，只是从"闸门"变成"随时可撤回"。

**工具侧由此缺三个动词**（当前都做不到）：申请移出队列、把任务指派给对话里的 agent（不带租约）、把任务标记为完成（`complete` 现在在 USER_ONLY 里被拒）。这三个正是 T-14 已需要的机制再加上第 3 条的"申请"模式。

**架构（用户给出的图）：四个参与者，四条边。** 左下与左上是**用户**；上方是**对话Agent**（与用户「对话」）；下方大方框是**任务系统**（用户与它「交互」），WorkAgent 住在它**里面**。

| 边 | 机制 | 现状 |
|---|---|---|
| 用户 —对话→ 对话Agent | DSH 原生会话 | ✅ 存在 |
| 用户 —交互→ 任务系统 | 面板路由（`webServer` + `fetch`） | ✅ 已有 |
| 对话Agent —下行→ 任务系统 | `task_center` 工具（申请 / 报告 / 读取） | ✅ 已有（三个伙伴动词待补） |
| 任务系统 —上行→ 对话Agent | 通知：`followup` / `send(…, wakeup)` | 机制已代码级确认（T-15），**尚未实现** |
| 任务系统 —→ WorkAgents | **框架触发**（spawn / wake） | ❌ **不存在** |

**这张图给出的关键结论：任务系统里唯一缺失的部件是"触发 WorkAgent"。** 它就是 T-16 卡在 T-15 上的原因，也是图中唯一没有实现的边——其余四条边要么已在跑，要么机制已确认。所以下一步不是"加功能"，而是**把那一条边接上**：任务系统要有能力 spawn/唤醒 WorkAgent，而这依赖 `followup`/`send(wakeup)` 的运行时行为。

（图中那条注记「允许执行一些操作系统的命令和读取结果」我读作**对话Agent 自身的能力**——这正是它能把草稿里的活自己干掉的原因，与第 2 条一致。若你的意思是"任务系统授予对话Agent 该权限"，那是一条不同的设计，说一声我改。）

**对话Agent 是任务系统的使用者。** 它使用任务系统**暴露的方法**（创建任务、查看任务列表、查看任务详情…）。更准确地说：**任务系统对外是一个 API，用户与对话Agent 是它的两个客户端**——用户走面板（交互那条边），对话Agent 走工具（下行那条边）。

这解释了为什么 `task_center` 工具与面板路由**必须共用一份状态与同一套规则**（实现上就是 `state.mjs` + `service.mjs`）——它们不是两个系统，而是**同一个 API 的两个绑定**。

由此产生一条重要的简化：**把"哪些动词被禁止"换成"哪些方法需要用户同意"。**

| 类别 | 方法 | 行为 |
|---|---|---|
| 自由调用 | 创建 / 列表 / 详情 / 更新 / 领取自己的… | 直接生效 |
| **需要用户同意** | 发布 / 移出队列 / 关单（池内的工作）/ 强制释放锁 | 调用返回 `needs-consent` + 计划 → 用户确认 → 生效 |
| 框架调用 | spawn / 唤醒 WorkAgent | 那条尚不存在的边 |

于是原先那张 `USER_ONLY` 硬拒绝表（`publish` / `unpublish` / `complete` / `approve` / `force_unlock` …）**被一个规则取代**：它们不是禁区，而是**需要同意的请求**——正是第 3 条与依赖闭包已经设计出的两阶段机制。**一个机制，而不是一张不断变长的例外表。**

仍然与角色有关的只剩一条，而且它不依赖身份判定：**任务上的租约决定谁能关它**——不带租约（对话内伙伴的活）可自行标完成；带租约（池内的工作）须 `submit` 到待验收、由用户关闭。

**对外 API 暴露的是"关于工作的决定"，不是"谁去做这件工作的机制"。**

用户的补充：**"领取自己的活"不会出现在任务系统的对外 API 里**——那是系统内部要解决的事。据此划清界线：

| | 内容 | 谁能调 |
|---|---|---|
| **对外 API（决定）** | 创建 / 列表 / 详情 / 更新；发布入池（需同意）；移出队列（需同意）；关闭验收；锁的申请与强制释放（后者需同意） | 两个客户端：用户（面板）、对话Agent（工具） |
| **系统内部（机制）** | **领取 / 派发 / 租约 / 等待队列 / 唤醒 / 重试**——即"哪个 WorkAgent 何时拿到哪件工作" | 只有任务系统自己（那条"框架触发"的边） |

由此产生的修正：

- **工具里现在摆着 `claim` / `release` / `reserve`，这是把内部机制泄漏成了客户端方法。** 它们应当从对外表面移除。这是**简化**，不是增加。
- 因此前面说的"缺三个动词"其实是**两个**：**申请移出队列**（需同意）与**标记完成**。我原先列的"把任务指派给对话里的 agent 且不带租约"正是这种**不该出现在 API 里的内部机制**——对话Agent 要队列里的活，走"申请移出"，而不是"认领"。
- **关闭规则要按"任务在哪里"表述，而不是按租约表述**：池内的工作由用户关闭；对话自己的活由对话Agent 标记完成。前一条我用"租约"来表述，那是**把内部记账泄漏进了权限规则**——租约是内部的东西，客户端不该看见它来决定自己能做什么。
- 推论：**对话Agent 对自己那份活的对外动作只有"更新"与"标记完成"**（外加两个需同意的请求）。草稿本来就是对话的工作清单，因此**我连"开始做"都不必对外声明**——直接做、做完标记。

### 对外 API 与内部职责（完整清单）

**一、对外 API**（客户端 = 用户的面板、对话Agent 的工具；同一套方法，差别只在"是否需要用户同意"）

| 组 | 方法 | 说明 |
|---|---|---|
| 读 | `overview` / `list(filter)` / `show(id)` | 首屏聚合（计数+队列+待验收+我的活+锁）；查询；详情（含每条依赖**及其状态**、history） |
| 写·决定 | `create` / `update` / `cancel` / `reopen` / `block` / `unblock` | 内容与意图；`blockedBy` 属于 create/update，成环或悬挂即拒 |
| 收尾 | `close(id, evidence)` | 池内的活由用户关闭；对话自己的活由对话Agent 标记完成（同一次迁移，授权不同） |
| 池 | `publish(ids)` / `unqueue(id)` / `reorder(id, delta)` | 当调用者是对话Agent 时**需用户同意**；面板上的「领取」= `unqueue`（主人把活从池里拿回来），**不是**认领 |
| 锁 | `locks()` / `requestLock(path, taskId)` / `releaseLock(path)` / `forceRelease(path)` | 申请返回"已授予"或"排队位次"；**授予是内部的** |
| 设置 | `getSettings` / `setSettings` | 并发预算、运行锁等（用户） |

通道（不是方法）：**系统 → 客户端的推送**（T-7）。读靠 `list`/`show`，推是系统主动。

**需同意**是一条统一规则，不是例外表：`publish` / `unqueue` / `reorder` / `forceRelease` 由对话Agent 调用时返回 `needs-consent` + 计划，用户确认后生效；用户自己调用永不需要。实现即依赖闭包那个两阶段机制。

**记录原则（用户提出）**：系统 API 建全之后，`.agents/` 下的**状态与文档**（板子、方案、设置）**一律走 API**，不再直接改文件；**源码**仍走文件与 git。当前是**过渡期**（API 尚未建全），所以允许直接改文件——但这是临时的，不是常态。

一条诊断必须记下：**比文件更麻烦的 API 一定会被绕过。** 本次已经发生过一次——为了一次拿到 16 条任务的完整 spec，我直接读了 `tasks.json`，因为 `list`/`overview` 只返回摘要，读全要 N 次调用。所以这条原则要真正成立，API 必须**至少和文件一样省事**：`list` 要能带过滤地返回**完整记录**（含 spec / acceptance / history），而不是只给摘要。

**过渡期的边界很清楚**：方案文档 API（T-8）、设置（T-3）、"需同意"的调用（T-14）三件到位后，就该收口——之后 `.agents/` 下的一切改动都应当能在板上或工具的历史里看到，而不是只留在某次文件编辑里。

**二、内部职责**（"谁在什么时候做哪件事"——客户端看不见也不调）

| 职责 | 现状 |
|---|---|
| **派发 / 触发 WorkAgent**（从池里取活、选/启 agent、交接） | ❌ **完全不存在**——架构图里那条缺失的边 |
| 依赖就绪调度：只派发前置已完成的任务；某任务完成后重算哪些变就绪 | ❌ 不存在（它取代了"agent 排队"的机制，见下） |
| 租约与接管：池内任务的持有租约、续约、过期回收、崩溃重试 | ⚠️ 只有"标记过期不回收"，回收与重试没有 |
| 并发预算与运行锁（同时几件活、同时几个游戏实例） | ❌ 不存在（T-3 / T-4） |
| 锁的仲裁：预约队列、等待最久者优先、租约、存活回收、目录前缀 | ⚠️ 仲裁与"同提交授予"已有；**过期通知、releaseAll、目录前缀、PID/status 回收**缺（T-5） |
| 唤醒：让 WorkAgent 或对话Agent 得知"轮到你了" | ❌ 机制已确认（`followup`/`send(wakeup)`），实现没有；且**插件能否触达别人的 Agent 句柄待查**（T-15） |
| 推送内容与去重（给客户端的摘要） | ❌ 不存在（T-7） |
| 持久化与一致性（板子文件、CAS、冲突重放） | ✅ 已有 |
| 依赖校验（成环 / 悬挂 / 前置被取消） | ❌ 不存在（T-13） |
| 审计时间线 | ✅ 已有（每条历史都记 who/when/from/to） |

**三、这条划分带来一处简化，而且它修订了先前的第 4–5 条。**

既然**认领与派发都是内部的**，"agent 加入该任务的等待队列、前置完成后唤醒等待最久者"这个机制**不必存在**：调度器**根本不会把前置未完成的任务派发出去**。于是等待队列从"**agent 等任务**"变成"**任务等前置**"，唤醒从"按任务唤醒排队者"变成"**某任务完成后重算哪些池内任务变就绪，再派发**"——一次调度扫描，而不是一张张唤醒名单。

意图不变（前置未完成的工作不得开工），机制更简单，而且**没有"死掉的等待者占住队首"这个问题**——因为队列里根本没有等待者。原先为它设计的"唤醒租约"随之取消。

**补正一：没有「领取」这个东西。** 用户指出**领取按钮不需要存在**——「退回草稿」就已经完成了退队。于是：

- 面板里的「领取」删除；`unqueue`（= 退回草稿）就是**出池的唯一动作**，queued → draft。
- 出池后它就是草稿，也就是**对话/用户自己的工作**，于是它的完整生命周期是 **draft → done**（不经过 queued/claimed/in_progress）——这正是"对话自己的活不进池子"的必然结果，`done` 因此必须能从 `draft` 直接到达。
- `unqueue` 只适用于 `queued`（**尚未派发**）的任务。已经派发出去的任务不能被"退回草稿"从 agent 手里抽走，那种情况用「取消」。

**补正二：已派发的任务可能完不成。** 用户指出：调度器不会派发前置未完成的任务，**但已经派发出去的任务可能并未完成**。这暴露了简化漏掉的一种情况——**前置可能永远不会完成**。补齐如下：

| 情形 | 处置 |
|---|---|
| 前置未完成 | **不下发**，但必须在板上**显示在等谁**（不能变成看不见的滞留） |
| 已派发但停滞（agent 死掉/卡住） | 租约过期 → **回收回池** → 重试；**重试超限 → 标为失败**，不再静默重试到死 |
| **前置永远完不成**（被取消 / 重试超限 / 标失败） | 下游**标记为"依赖已破"并交给用户决定**：取消它、改依赖、或**强行放行**。绝不静默等待 |
| 用户选择强行放行 | `publish` 对"前置已取消"**默认拒绝**，但允许用户**显式覆写**——否则前置一旦被取消，下游永远无法发布。覆写要记进 history（审计得看得出来它是带着破依赖发的） |

即：**"派发门槛"只解决"不能提前开工"，它不解决"永远开不了工"。** 后者需要失败状态、重试上限、以及一条把"计划已坏"交回人手里的路径。

### 派发怎么实现（调查结论，已可用）

**判定：插件能直接触达并唤醒另一个会话**——不需要框架侧配合，也没有绕过授权。

| 需要的能力 | 机制 |
|---|---|
| 找到能派发的人 | `ctx.agents.list()` + `agentTeams.tryMembership(a)?.role === 'lead'`（`tryMembership` 不抛） |
| 知道谁空闲 | `agentTeams.listMembers(lead)` → `status: 'running' \| 'inactive' \| 'provisioning' \| 'failed'` |
| 发消息并**叫醒它** | `agentTeams.sendMessage(lead, {target: name, content, signal})` → 目标空闲则 `coldResume`（从持久会话重建 Agent 并跑一轮） |
| 不轮询地等变化 | `agentTeams.waitForChange(caller, timeoutMs)`（10s–1h） |

**关键约束**：`caller` 必须是**真实的 live Agent 实例**（由 `ctx.agents.get()` 取得）——服务会校验 `agents.get(sender.id) === sender`，**传自造的 `{id}` 必失败**。**目标按名字解析**：每次派发前重新 `listMembers`，不缓存名字。信箱上限 **64 条**、单条 **65536B**。

**三层路径**：**A** `agentTeams`（推荐；需 `include:agent-team` 行在，本 profile 已满足）→ **B** `subagents.prompt({parentSessionId, childSessionId, delivery:'queue'})`，只要两个字符串 id、覆盖面更广（不限 Team），但 `authorizeLineage` **只允许直接子级**、父须 live、one-shot 子级 `NOT_RESUMABLE` → **C** 把"可派发清单" `steer` 给 Lead，由 Lead 用它自己的 `spawn_teammate`/`send_message` 执行（永远可用，但**最易死循环**、可观测性最差）。三条路径写同一份 `dispatch` 字段，降级不需要迁移数据。

**防重复派发是这块的核心风险**（不是技术可行性）：幂等键 `taskId+attempt`；派发前先读 `task.dispatch`，`accepted|queued` 且租约未过期即**不重发**——**`queued` 也是成功**（官方原话："A successful send is already durable even when its result says queued; do not resend it."）；`inFlight` 集合与 `state.mjs` 的内存同级，让工具/面板/事件三条入口共享；`queued → claimed` 只做**一次性跃迁**；派发内容带 "Do NOT dispatch; you are the assignee"。

**首次探测（已实测——一次重启后取 `GET /godot-bridge/task-center/dispatch`）**：`hasAgents: true` · `hasAgentTeams: true` · `agentCount: 1` · `membersReadable: true`；Lead 由 `tryMembership(…).role === 'lead'` 正确解析，**就是本对话所在的会话**；花名册 `[{name:'lead', role:'lead', status:'running'}]`。**那条唯一的推断已被证实**：`agent/status` 在 `ctx` 与 `ctx.root` **两个通道都到达**（同一事件、同一时间戳）——**profile 行确实能收到 agent 状态事件，所以派发可以做成反应式，不需要轮询**。

仍未实测的只剩 **`sendMessage` 这个写动作**（探测刻意不发消息）——它是端到端实验的第一步。另一处（T-17）已有结论：`agentTeams.createTask` 与我们的板子是**不同层**，不合并，只复用其 `waitForChange` 一类的机制。

**Lead 从哪来，以及没有 Lead 会怎样。** `agentTeams` 的每个方法都要求 `caller` 是一个**真实活着的 Agent**——插件自己没有身份，只能**借用**。可借的身份里最强的是 Lead：**spawn 要求 caller 必须是"exact live Lead Agent"**，而发消息只要求"exact live sending Team member"（所以已有的成员也能发）。

但 **Lead 不是我们发明的**，它是 harness 中 Team 的**根会话**；而且**单个会话本身就是一个"一人 Team"**——首次探测时 `agentCount: 1`、`members: [{name:'lead', role:'lead', status:'running'}]`、**零个 teammate**，Lead 照样解析得出来。因此：

- **"没有 Lead" ≡ "没有任何根会话活着"** ≡ 没人在。
- 此时**板子完全不受影响**（草稿、面板、锁、依赖、历史都照常），**只有池子没人可派**，派发明确回 `no-lead` 并说明"任务留在队列里，等有会话再说"。
- 根会话再出现时派发即可继续——`agent/created` 就在事件目录里，所以这是可恢复的，不是终态。

**WorkAgent 不可能脱离 Lead 存在**：它们是"Team Lead 的 continuable 直接子级"，而 spawn 又要求 Lead 凭据。所以"无 Lead 的池子"**不是我们可以选的变体**，那是 harness 的形状。我们能选的是**谁当那个根**——今天是本对话所在的会话，将来是你的框架层；插件侧的契约不变。

这条边界的准确表述：**板子不依赖任何 Team；池子依赖"有一个根会话"。** 前者是大多数时候在用的东西，后者只在真正要派发时才需要。

### 发布是依赖闭包

**发布一个任务 = 发布它的依赖闭包**，但只拉**还是草稿的**依赖（用户要求："若要发布任务，则要发布被其依赖的任务，要有明确展示和确认过程"）。逐状态：

| 依赖状态 | 发布时 |
|---|---|
| `draft` | **必须一起发布**（级联） |
| `queued` / `claimed` / `in_progress` / `review` / `done` | 已发布过，不动 |
| `cancelled` | **拒绝**并点名：前置被取消了，这条的计划是坏的 |
| id 不存在（悬挂） | **拒绝**并点名：数据错误，不该被吞掉 |
| 成环 | **拒绝**（见下） |

闭包**传递**：A 依赖 B、B 依赖 C，发布 A 需连 C 一起。

三条伴随要求，缺一这条规则就不成立：

- **写入时必须拦环。** 今天 `blockedBy` 写入毫无验证，A→B→A 存得进去（AI 分两遍加依赖时很容易造出来）。闭包算法遇环会死循环——visited 只能防死循环，那是掩盖问题。**会成环的写入直接拒绝。**
- **队列位次按拓扑排。** X 与前置 T-5 一起发布时，T-5 必须排在**前面**，否则队列头是 X，agent 会先领走前置未完成的任务（见下一条）。
- **认领端目前没有任何检查。** 这是本条暴露出的洞：今天一个任务的 `blockedBy` 未完成，它照样能被领取——**依赖只影响看到的字，不影响行为**。发布端由此规则补上；认领端建议**报告而不拒绝**（agent 有时合理地想提前开工），但要在板子与工具结果里**显式可见**。认领端是否硬拦，作为独立问题待定。

**确认过程做成两阶段调用**，这样客户端不可能"顺手"级联：

```
POST {action:'publish', id:'T-2'}
→ {ok:false, code:'needs-confirmation', cascade:['T-5','T-8','T-2']}

POST {action:'publish', id:'T-2', confirm:true}
→ 执行
```

闭包只有它自己时一步完成，不打扰用户。

**"明确展示"分两处**：确认框按**依赖顺序**列出将被发布的任务；任务详情里每条依赖**带上它自己的状态**（`T-5 草稿` vs `T-5 已完成`）——"是草稿"正是触发级联的原因。

### 方案文档

方案**不是新存储**，而是一种文档类型（front matter 即元数据）：`type: proposal`、`status`、`revision`、`sessions`、`decisions`、`open_questions`。

状态机：`draft → discussing → settled → superseded`（旁支 `abandoned`）。

**核心不变式：只有 `settled` 的版本可以被拆解；每个任务记录 `proposal_ref` + `proposal_revision`。** 否则方案一改版就无法判断哪些任务过期。方案改版后"从新版本重新拆解"是一等操作，旧版本拆出的任务标 **stale 交用户处置，不自动删除**。

## 五、命名

| 概念 | 名称 |
|---|---|
| 一场讨论 | 议题 / Topic（就是一个会话，不发明新词） |
| 冻结下来的方向 | **方案 / Proposal** |

**不采用 AIM**：DSH 已有 `goal`，再造近义词会凑出五个同义概念；首字母缩写不自解释，翻译与双语读者都拿不到语义；而且它把"讨论"和"产物"盖成一个词——两者的差别（产物需要冻结、讨论不需要）恰恰是本设计最值钱的地方。

**方案定稿后，它的生命周期就是一条 ADR**：`settled` 是"已决定"，`superseded` 是"被取代"。所以：方案 = 讨论稿 + 定稿；定稿即决策记录。

## 十、打包：一个包、两个组件行

**卡片数 = bundle 数；组件数 = 行数。** 这两件事是独立的，所以"任务中心是 godot-bridge 的一个组件、而不是一个独立插件"并不需要把代码合成一个文件：

```yaml
# godot-bridge/cordis.patch.yml
- insert:
    - id: tool-godot-bridge
      name: godot-bridge
    - id: task-center
      name: godot-bridge/task-center      # 包内子路径行
```

行名可以是包内子路径——官方组合就是这么挂 `@deepseek-ai/dsh-plugin-manager/tools` 的，而那个行模块**只导出 `inject`/`apply`，没有 `name`**（插件身份由包入口持有）。所以宿主半可以按职责拆文件，客户端半不行。

### 被否决的做法：拆成独立包

曾实现过（提交 `6cd240c`，后被 `git revert` 退回），理由是"一包一个 client bundle"与"不把开销摊给所有用户"。**否决原因是分发**：`dsh plugin add github:Smalldy/godot-bridge` 只装一个包，独立包要求用户多装一次、或要求 godot-bridge 依赖一个必须另行发布的包。**"装/更新 godot-bridge 就能用"是硬要求**，它优先于上述工程偏好；而"不摊开销"这一点也因为任务中心今天只带来一条命令和一个面板而基本不成立。

### 职责分离

- **宿主半：可以真拆文件。** 宿主是真 ESM，相对导入随便用；每个职责还可以是独立的行、独立生命周期。`/task` 在 `plugin/task-center/index.mjs`，板子在 `board.mjs`、模型在 `service.mjs`，都是同目录兄弟模块相对导入。
- **客户端半：机制上只能一个文件。** 一个包只解析一个 `exports["./client"]`，且它是 classic script——没有相对 require、没有动态 import（只有 9 个平台基座 specifier，或 `dsh.client.external` 里指名的**别的包**的 bundle）。所以要么用区域分段，要么引入构建步骤，要么**把逻辑搬到宿主**——最后这条才是真正的解法：客户端今天 2621 行里大半是 mock store（状态机、锁仲裁、种子数据），这些规则本来就该住在宿主，与 `task_center` 工具共享、也才可测。任务 2 落地后客户端应缩到视图 + fetch（数百行），届时一个文件不再难受。

### 热重载的实际边界（实测）

**宿主源码改动只能靠重启加载**，实测两条：

- `hmr` 以 `root: []` 启用，只监听 profile manifest 与两份用户 patch，**不监听插件源码**。
- **bundle 的 disable/enable 不能当重载用。** 提交 `bc5f68f`（给 `/task` 加板子摘要）之后做过一次 `set_bundle false` → `set_bundle true`，两次都报 `application: applied`；随后敲 `/task`，信号完整到达但**不带摘要**。推断是硬的：`await boardDigest()` 在 `agent.steer()` **之前**，若它抛异常就不会有任何消息被送出；消息到了 ⇒ 它返回了字符串；新代码若在内存里，摘要必然出现在消息末尾。**所以内存里仍是旧模块——结论是实测的。** 最可能的机制是旧那一代注册的 `/task` 未被销毁，新注册撞名后由本模块自己的 try/catch 记 warn 并跳过，于是旧 handler 继续应答；**机制是推测，结论不是**。随后一次重启，同一敲法立刻带上了摘要——**换掉模块的唯一途径是重启**，闭环。

推论：宿主源码的开发循环 = 每次重启，或打开 HMR 的源码监听（`root: ["."]`，注意插件是 `link:` 进来的，未必覆盖到）。bundle 自己的 patch 变化需要重启这一条，在第二个行出现时已单独确认过。
